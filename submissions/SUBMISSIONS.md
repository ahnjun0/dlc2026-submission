```
sub-015 (4096)  0.79903 = **664**/831        **−4문항**
```

**사전 등록선(664 이하 = 기각)에 정확히 걸렸다.** val460 의 −1 과 부호가 같다.
**문샷 8192 를 D-Day 구성으로 유지한다.**

## sub-016 — 2단 분할 + confirm=16 (2026-08-26) · **미채택 · 시간 fallback 으로 문서화**

**질문**: 1단계를 두 단으로 쪼개고(16표에서 12표 이상이면 조기 확정) `confirm` 을 30→16 으로
낮추면, 정확도를 지키면서 D-Day 시간을 반으로 줄일 수 있는가?

```
생성 배치   sub-014 와 **완전히 동일** (exp-082_rehearsal2 + exp-101_cascade)
            **GPU 0시간** — v2 생성물의 앞 16표를 잘라 쓰고 조립만 다시 했다
회귀 검증   기본값으로 재조립 → sub-014 와 **0행 차이** (배포 스크립트 무변경 확인)
분기        1단계-a 조기 확정 570/831 (68.6%) · 문샷 호출 369 → **176 (44.4% → 21.2%)**
두 제출물이 갈리는 문항 **5**
```

**결과**
```
sub-014 (현행)      0.80385 = **668**/831
sub-016 (2단+cf16)  0.80144 = **666**/831        **−2문항**
```

**판정: 미채택.** 사전 등록 문언(*"666 이상 채택"*)으로는 채택이지만,
**그 괄호 안의 근거 — «동률 이내면 시간 절감이 순이득» — 가 반증됐다.**
리허설 실측으로 현행 구성이 **12.3시간**이고 24시간 안에 여유 있게 들어가므로,
**지금은 시간이 필요 없다.** 시간 가치가 0에 가까운데 −2문항은 실제 비용이다.

> **사전 등록 설계의 결함으로 기록한다**: 조건에 «시간이 필요한가»를 넣었어야 했는데
> 시간 절감을 **무조건 이득**으로 놓았다. 앞으로 «자원 절감» 카드는
> **그 자원이 실제로 제약인지**를 채택 조건에 명시할 것.

### 그러나 버리지 않는다 — **비용이 측정된 fallback** 이다

CLAUDE.md 에 `DDAY_CONFIRM=26` 이 *"시간 부족 시"* 대비책으로 적혀 있었으나 **비용을 몰랐다.**
이제 안다 — **5시간을 2문항에 산다.**

```
주 구성    캐스케이드 cf=30 · margin=5           **668/831** · D-Day **12.3h**
fallback  2단(16표≥12) + cf=16                 **666/831** · D-Day **7~8h**
발동 조건  ① test 2단계 진입률이 44% 를 크게 넘을 때 (외부 문항에선 70.2% 였다 → 17h+)
           ② 장비가 PRO 5000 급에 못 미칠 때
           ③ 00:00 시작이 지연됐을 때
```
**미완주는 −수십 문항이므로, 그때는 −2를 내고 완주하는 것이 옳다.**

**생성 커맨드**
```
python src/eval/build_cascade.py --v2 <v2> --partner <moonshot> --third <contest> \
  --input <test.csv> --tier1-n 16 --tier1-confirm 12 --confirm 16 \
  --out submissions/sub-0NN.csv
```

## sub-017 — 3단계 제거 ablation (2026-08-26) · **3단계 유지 확정**

**질문**: 3단계(경시STaR 증원)가 LB 에서 실제로 기여하는가?
그동안 인용해온 `+3`(sub-014 668 vs sub-012 665)은 **«캐스케이드 전체 vs 전량 풀링»** 이라
1·2·3단계 효과가 섞여 있었다. **3단계만 뺀 대조는 처음이다.**

```
생성 배치   sub-014 와 **완전히 동일** · **조립만 변경** (margin=−1 → 3단계 발동 0 확인)
            GPU 0시간 · 학습 0
대조군      sub-014 = 668/831 (채점 완료)
두 제출물이 갈리는 문항 **33**
```

**결과**
```
sub-014 (3단계 있음)   0.80385 = **668**/831
sub-017 (3단계 없음)   0.80024 = **665**/831
                                  **Δ_LB = +3문항**
```

**판정: 유지.** 사전 등록표(`docs/stage3-ablation-preregistration.md`)의
**`Δ ≥ +3` → 유지 (실용 MDE까지 독립 확인)** 에 해당한다.
val 3시드(382.00 → 385.00 = +3.00)와 **방향·크기가 일치**한다.

**단 전이 부족은 여전하다**: val +3.00(460문항)을 831 로 환산하면 +5.4 를 기대해야 하는데
실측 +3 이다. 부족분 **−2.4** 로 `exp-101`(−2.4)과 같은 크기다.
→ **val·LB 를 둘 다 잰 6건이 전부 같은 방향**이 됐다 (부호검정 p=0.016).

**기제 (val 에서 분리, `docs/why-cascade-works-2026-08-26.md` §8)**
```
추가 표 수를 32로 고정하고 구성만 바꾼 비교
  경시STaR **+3.00** > v2 64표증량 +2.67 > v2 32 +1.67 > v2 16+문샷 16 +1.00 > **문샷 32 −2.00**
→ 접전에서 **문샷 표를 늘리면 해롭고 v2 계열을 늘리면 이롭다** = 조건부 재가중
→ 단 경시STaR > v2 재뽑기 이므로 순수 재가중도 아니다.
   **2단계는 «다른 체제», 3단계는 «같은 체제 · 다른 데이터»** 가 맞다
```

**사전 등록대로 여기서 종료한다** — 문턱·멤버·표 구성을 추가 탐색하지 않는다.
**D-Day 구성 확정**: v2 32 → (최다<30) 문샷 32 → (격차≤5) 경시STaR 32 · **12.3시간**.

**생성 커맨드**
```
python src/eval/build_cascade.py --v2 <v2> --partner <moonshot> --third <contest> \
  --input <lb.csv> --confirm 30 --margin -1 --out submissions/sub-017_no-stage3.csv
```
